很多刚接触 CubeX 的老哥常常带有一连串疑惑：“为什么网关不改主路由也能加速？”、“容器挂了真的不断网吗？”

[size=3][b]Q1：如果跑 CubeX 的容器挂了，主路由的 DNS 会自动及时使用备用的吗？[/b][/size]

[b]答：不仅会自动及时切换，而且全家压根感觉不到网络中断！底层有三道坚实防线：[/b]

1. [b]终端压根没改过 DNS[/b]：全家所有手机、电视、平板，DHCP 获取到的 DNS 始终是主路由（例如 10.0.0.1），终端从不直连 CubeX 容器的 53 端口；
2. [b]毫秒级应用看门狗双向脱钩（以 RouterOS 为例）[/b]：主路由通过 Netwatch 每隔 2~3 秒对 CubeX 状态进行应用级心跳探测。一旦容器被强杀或死机，50ms 内立刻触发脱钩脚本，自动注销 DNS 劫持规则，主路由 DNS 解析秒级回退至备用公共 DNS（如 223.5.5.5 / 119.29.29.29），国内网页与视频不受丝毫影响；
3. [b]198.18 黑洞防外泄兜底[/b]：主路由预埋了低优先级的 [color=#0066cc][b]198.18.0.0/15[/b][/color] 本地黑洞路由。哪怕在容器重启、部分终端还保留上一秒 Fake-IP 缓存的短暂微秒，残余报文在主路由被黑洞瞬间静默吸收，绝对不会外泄到光猫产生证书伪报错（[color=#0066cc][b]NET::ERR_CERT_COMMON_NAME_INVALID[/b][/color]）。
[hr]
[size=3][b]Q2：为什么全家所有设备网关和 DNS 都指向主路由，也能实现网络加速？[/b][/size]

[b]答：核心在于「智能静态回指路由」的精妙协同！[/b]

- 传统旁路由强迫每台设备把网关改成它，所以它成了局域网的“唯一瓶颈”；
- CubeX 的做法是：让全家设备安安心心把网关和 DNS 指向主路由。我们只在主路由中添加一条静态回指路由（[color=#0066cc][b]198.18.0.0/15[/b][/color] 指向 CubeX IP）。
- [b]国内流量[/b]：主路由发现是国内 IP，直接芯片级 FastTrack 硬件满血直通光猫，完全不经过 CubeX；
- [b]国际流量[/b]：主路由命中 198.18 静态回指规则，毫秒级注入 CubeX 容器处理。全家既享受了极速分流，又拥有了主路由物理线速直出的强劲性能！
[hr]
[size=3][b]Q3：CubeX 会不会修改主路由器核心配置或留下安全隐患？[/b][/size]

[b]答：绝对不会！CubeX 遵循严格的「宿主共生零侵入」原则。[/b]

- CubeX 运行在独立的沙盒容器（LXC / Docker）中，代码纯 Go 编译，零历史残留依赖，纯内网安全监听；
- 对主路由的联动仅限于标准 REST API 或一条普通的静态路由条目，随时在主路由后台一键禁用或删除，彻底告别“请神容易送神难”的顾虑。
[hr]
[size=3][b]Q4：PT 下载和局域网 NAS 传输会走 CubeX 吗？会不会有瓶颈？[/b][/size]

[b]答：100% 走主路由物理芯片满血直出，零性能瓶颈！[/b]

CubeX v9.9.0 独家实装了「🎬 影音/NAS 专属分流模式」：
- PT/BT 协议、P2P 握手与大流量下载，100% 走运营商物理宽带直连直出，跑满 2.5G/万兆线速；
- 局域网内电视机拉取 NAS 原盘播放，数据流在主路由二层交换芯片内完成转发，完全不经过旁路由；
- 只有海报墙元数据刮削（TMDB/TVDB）与 Docker 镜像源走低延迟加速通道，两全其美！
[hr]
[size=3][b]Q5：双核混动（sing-box × Mihomo）比单核有什么实际优势？[/b][/size]

[b]答：兼顾“极致轻量”与“完备兼容”的完美平衡。[/b]

- [b]sing-box v1.14+[/b]：轻量极速，内存开销极低（仅 ~28MB），路由决策微秒级，适合长期日常省心托管；
- [b]Mihomo (Clash.Meta)[/b]：规则生态极其成熟，高级策略组与流媒体规则全面；
- CubeX 通过统一的 IR 中间表示层完成双向编译，单次切换耗时仅 [b]234ms[/b]，配合 Stale Killer 清道夫机制，实现无感热备与动态容灾，永远多一份可靠底牌！
